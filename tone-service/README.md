# T-one STT микросервис

Сервис распознавания русской речи на модели [T-one](https://github.com/voicekit-team/T-one)
(Т-Банк, Apache-2.0). Работает на CPU, GPU не нужен: инференс идёт на ONNX Runtime.

Сервис принимает аудио и возвращает текст. Основной потребитель — backend MedScribe,
но сервис не привязан к приложению и может работать отдельно.

## Эндпоинты

Определены в `app.py`:

- `GET /health` — возвращает `{"ok": true, "diarization": true, "gigaam": "absent"}`. `ok` — модель распознавания
  загружена (по нему смотрят приложение и healthcheck). `diarization` — загружена ли разметка
  по голосу; если `false`, распознавание работает как раньше, без меток голоса. `gigaam` —
  состояние второго движка (см. раздел «GigaAM v3» ниже).
- `GET /engines` — состояние движков для кабинета: `tone.ready` и блок `gigaam` (`state`,
  `loaded`, `downloaded_bytes`, `total_bytes`, `error`, `model`).
- `POST /engines/gigaam/prepare` — запускает в фоне загрузку GigaAM (если файлов ещё нет) и
  загрузку модели в память. Отвечает `202` и `{"state": ...}`. Если уже идёт или готово, ничего не меняет.
- `POST /engines/gigaam/release` — выгружает GigaAM из памяти. Файлы на диске остаются.
- `POST /transcribe` — принимает сырое аудио в теле запроса (любой формат, который
  понимает ffmpeg: webm, ogg, wav и др.). Параметр `?engine=tone` (по умолчанию) или
  `?engine=gigaam`; любое другое значение — `400`. Возвращает:

  ```json
  { "text": "...", "duration_sec": 312.4,
    "phrases": [ { "start": 0.52, "end": 3.10, "text": "...", "speaker": 1 } ],
    "diarization": "ok", "engine": "tone", "engine_fallback": null }
  ```

  `phrases` — фразы с временем начала и конца в секундах; при пустом или неудачном
  декодировании это `[]`. `speaker` — номер голоса 1..N, только при `diarization: "ok"`,
  иначе `null`. `engine` — каким движком расшифровано на самом деле. `engine_fallback` —
  почему запрошенный GigaAM не использовали: `not_ready` (модель не готова) или `error`
  (сбой GigaAM); иначе `null`. Статусы `diarization`:
  - `ok` — голоса разделены, у фраз есть `speaker`;
  - `single` — найден один голос, метки не нужны (`speaker` = `null`);
  - `skipped` — разметка не запускалась: аудио короче 3 с или нет фраз;
  - `off` — разметка выключена (`DIARIZATION=off`) или модели не загрузились;
  - `failed` — ошибка разметки; текст и фразы отдаются как обычно, без меток.
- `WS /stream` — потоковое распознавание. Клиент шлёт непрерывный поток PCM int16,
  mono, 8 кГц; сервис отдаёт фразы по мере готовности в виде `{"text": "..."}`.
  Текстовое сообщение `flush` завершает поток. Голоса в потоке не размечаются.

## Разметка по голосу (диаризация)

`diarize.py`: сегментация pyannote segmentation-3.0, отпечатки голоса 3D-Speaker CAM++ и
кластеризация (sherpa-onnx). Модели вшиты в образ в `/opt/diar`, их скачивает
`fetch_diar_models.py` при сборке с проверкой sha256. При работе сервис в сеть не ходит
(единственное исключение — загрузка GigaAM по команде, см. ниже).

- **Выключатель.** `DIARIZATION=off` выключает разметку. Любое другое значение, в том числе
  не заданное, оставляет её включённой. В `docker-compose.yml` по умолчанию `on`.
- **Порог.** Порог по умолчанию задан в `diarize.py` (`DEFAULT_THRESHOLD`). Переменная
  `DIARIZATION_THRESHOLD` нужна только для отладки. Чем ниже порог, тем охотнее голоса
  делятся на отдельные: при слишком низком синтетические голоса (TTS) дробятся на много
  кластеров. Compose не передаёт эту переменную в контейнер, без своего override-файла
  она не действует.
- **Слишком много голосов.** Если сервис нашёл больше `MAX_SPEAKERS` голосов (константа в
  `diarize.py`), запись пересчитывается ровно на два голоса: врач и пациент.
- **Минимум.** Короче 3 с разметка не запускается (статус `skipped`): голоса на таком
  отрывке не различить.
- **Максимум.** Дольше `DIAR_MAX_SEC` секунд (по умолчанию 1320, то есть 22 минуты) разметка
  тоже пропускается (`skipped`), текст отдаётся как обычно: цена разметки растёт с длиной
  записи. Клиент режет запись на отрезки до 20 минут. Переменная читается один раз при
  старте сервиса; Compose её в контейнер не передаёт, без своего override-файла она не
  действует.
- **Параллельность.** Тяжёлые запросы `/transcribe` выполняются по одному (замок в
  `app.py`): так ограничены память и нагрузка на процессор. Потоковый `/stream` замка не
  берёт и работает одновременно с ними: состояние распознавания в T-one хранится не в
  объекте pipeline, а передаётся снаружи, сессия ONNX Runtime потокобезопасна, декодер
  состояния не имеет.
- **Сборка без GitHub.** Образ при сборке качает модели с GitHub releases. Если GitHub
  недоступен, укажите зеркало: `--build-arg DIAR_MODELS_BASE=<адрес>`. Зеркало должно
  повторять структуру путей GitHub releases. Подробнее — в
  [CONTRIBUTING.md](../CONTRIBUTING.md#локальная-сборка).

## GigaAM v3 (второй движок итоговой расшифровки)

`gigaam.py`: модель GigaAM v3 (Сбер, MIT), вариант `v3_e2e_ctc` в int8 (с пунктуацией и
нормализацией), в ONNX-конвертации [istupakov/gigaam-v3-onnx](https://huggingface.co/istupakov/gigaam-v3-onnx).
Отрезки речи ищет Silero VAD. Запускается пакетом `onnx-asr` (numpy и onnxruntime, без torch).

GigaAM используется только для итоговой расшифровки: `POST /transcribe?engine=gigaam`
(после «Завершить», в режиме стенографа и по кнопке «Расшифровать»). Живой текст во время
приёма (`/stream`) остаётся на T-one.

- **Загрузка по команде.** Веса в образ не вшиты, при старте сервис ничего не скачивает.
  Загрузку запускает приложение через `POST /engines/gigaam/prepare` (кнопка в кабинете).
  Файлы около 227 МБ лежат в `HF_HOME` (в Docker — том `tone-models`, папка `gigaam/`).
- **Зеркало.** Адрес берётся из `HF_ENDPOINT`, тот же, что для T-one (`.env`, раздел 4.1
  инструкции). Значение должно начинаться с `http://` или `https://`.
- **Проверка файлов.** Каждый файл закреплён ревизией репозитория, размером и sha256
  (`MANIFEST` в `gigaam.py`). Файлы пишутся во временную папку и переименовываются только
  после проверки всех. Сбой сети повторяется до 3 раз. Неверная сумма — ошибка `checksum`.
  Перед загрузкой проверяется место: нужно около 300 МБ свободно.
- **Состояния.** `absent` (не скачана), `downloading`, `verifying`, `loading`, `ready`,
  `failed`. Причины ошибки в `error`: `network`, `checksum`, `disk_space`, `load`, `unknown`.
  Остатки прерванной загрузки удаляются при старте.
- **Память.** Модель загружается в память при первом использовании. На Mac (Docker, arm64,
  8 ядер) поверх T-one добавилось около 0,1–0,4 ГБ. После `POST /engines/gigaam/release`
  память освобождается, файлы остаются.
- **Без сети после загрузки.** Когда файлы скачаны и проверены, GigaAM работает офлайн.
- **Откат на T-one.** Если GigaAM не готов, `/transcribe?engine=gigaam` расшифровывает через
  T-one с `engine_fallback: "not_ready"`. При сбое GigaAM в лог пишется только тип ошибки
  (текст не логируется), расшифровка идёт через T-one с `engine_fallback: "error"`.
- **Фразы.** У GigaAM фразы совпадают с отрезками VAD. Разметка по голосу (`speaker`)
  выполняется как обычно, T-one для текста при этом не запускается.
- **Замер.** Один тест на Mac: 70-секундный диалог двух голосов. T-one: 433 символа за 13 с,
  GigaAM: 772 символа за 5 с, голоса разделены верно в обоих случаях. Длинных записей
  не проверяли. Сравнение двух движков на своём аудио: `tools/compare_engines.py`.
- **Персональные данные.** `tools/compare_engines.py` пишет в папку вывода полные расшифровки
  (`response_tone.json`, `response_gigaam.json`). На реальных записях это персональные данные:
  указывайте временную папку вне репозитория и удаляйте её после сравнения.
- **Полностью офлайн.** Чтобы T-one при старте вообще не обращался к HuggingFace (веса уже в томе),
  задайте `HF_HUB_OFFLINE=1`. Скачивание весов GigaAM по команде врача от этой переменной не зависит.

## Запуск в Docker

Сервис поднимается автоматически вместе с приложением через корневой `docker-compose.yml`
(сервис `tone`, образ берётся из GHCR). Отдельно его запускать не нужно:

```bash
docker compose up -d
```

Сборка образа из исходников описана в [CONTRIBUTING.md](../CONTRIBUTING.md#локальная-сборка).

Наружу порт 5001 не публикуется: сервис доступен только остальным контейнерам compose.
Модель при первом старте скачивается, поэтому healthcheck ждёт до 20 минут.

Если HuggingFace недоступен из вашей сети, укажите зеркало в файле `.env` рядом с `docker-compose.yml`:

```
HF_ENDPOINT=https://адрес-зеркала
```

Затем выполните `docker compose up -d`: сервис `tone` пересоздастся с новой переменной. Compose подставляет её из `.env` сам (`${HF_ENDPOINT:-https://huggingface.co}` в `docker-compose.yml`).

## Запуск локально без Docker

Нужны Python 3.11, ffmpeg, cmake и boost (сборка KenLM из исходников).

Для macOS:

```bash
brew install ffmpeg cmake boost
```

Далее из папки `tone-service`:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app:app --host 127.0.0.1 --port 5001
```

Для Linux установите системные пакеты `ffmpeg`, `cmake`, `libboost-all-dev` и
`build-essential` вместо brew.

Проверка:

```bash
curl -s http://127.0.0.1:5001/health
```

## Грабли

- **Пакет `tone` на PyPI — чужой.** Официальный T-one на PyPI не публикуется. Пакет `tone`
  с PyPI к T-one не относится, его ставить нельзя. Нужная версия ставится из git
  и закреплена на коммите в `requirements.txt`. Не заменяйте эту строку на `pip install tone`.
- **Модель скачивается при первом старте.** Веса весят около 5 ГБ и загружаются с
  HuggingFace. Место для них задаёт переменная `HF_HOME` (в Docker — `/models`, в volume
  `tone-models`). Первый старт может занять заметное время.
- **Процесс занимает около 5 ГБ RAM.** Учитывайте это при выборе сервера или
  лимитов контейнера. После загрузки GigaAM в память добавляется ещё около 0,1–0,4 ГБ.
- **Аудио внутри ресемплится в 8 кГц.** `read_audio` всегда приводит звук к 8 кГц,
  даже если входной файл был 16 кГц. Длительность считается именно по 8 кГц.
